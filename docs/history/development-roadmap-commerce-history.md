## 一、项目目标与共同约束

目标是独立的电商智能客服 Agent Backend，V1 完成订单查询、订单取消、退款审批和有来源的知识库问答，并在核心业务稳定后接入用户长期记忆。

- 技术体系：Python、FastAPI、LangChain、LangGraph，优先采用 PostgreSQL 生态并评估 pgvector。
- 架构：Supervisor + Specialist Agents + Workflow Subgraphs + Shared Infrastructure。
- 主调用方向：Route → Service → Runtime → Graph。
- Supervisor 负责意图、澄清、委派和协调；Order、AfterSales、Knowledge 专业子图负责领域决策；确定性业务子图控制规则检查和副作用顺序。
- 首版每轮串行选择一个专业任务，同一已验证会话绑定稳定 thread，同一时刻只允许一个活动业务 workflow。
- 主图保存公共历史与结构化结果，专业子图保存私有消息和业务状态，通过显式白名单映射传递。
- 归属、资格、金额和写入幂等由 Domain Service 保证，实际写入时再次检查。
- 执行生命周期独立于 SSE；审批不能由普通聊天伪造；支付超时先核对结果，不无条件重复退款。

V1 开发期交付采用真实模型、Apifox 可信入口模拟，以及具有业务规则和实际本地状态变更的模拟订单/支付服务。真实 Java 后端与真实支付的接入情况单独记录和验收，模拟业务与资金属性必须明确。

相关依据：[开发规范](../../AGENTS.md)、[Graph 协议](../graph-protocol.md)。旧架构设计和旧 02 设计、实施计划已按用户要求删除，整体架构约束与执行规划统一以本文为入口。

### 3.3 的执行、Checkpoint 与崩溃边界

- 首版优先采用单进程执行任务、PostgreSQL 任务记录和启动核对，具体接口和状态在该环节详细设计中确认。
- 持久任务记录标识受理、运行和结果，不代表 Python 协程能够跨进程继续运行。
- 基础 Checkpoint 的资源接入、读写、稳定 thread 关联和跨轮续接归 3.3，不整体推迟到 6.1。
- 3.3 明确接入 PostgreSQL 基础 Checkpointer、普通快照/澄清续接和跨 Run State 准备；当前 InMemorySaver 不是重启恢复能力。6.1 不再重复基础接入。
- 同 thread 的新输入、重试和恢复统一互斥；数据库活动工作流约束和进程执行互斥分别承担持久约束和运行控制。
- 正常异常退出与进程崩溃分别定义处理方式。不能安全恢复的任务须有明确的待核对、失败或人工处理语义，不能永久停留在无法解释的运行状态。
- 仅对安全性与幂等已经确认的操作恢复或重试；无法判断是否生效的副作用先核对。完整审批和副作用重放安全在 6.1 及业务环节验收。

### 3.5 的断开、重连、重放与查询边界

- 断开仅释放订阅，不撤销已受理执行或已完成操作。
- 重连针对原执行标识查询状态、订阅后续事件，不自动再次受理、重新执行或触发审批 resume。
- 首版内存队列不承诺持久事件重放或 Last-Event-ID 断点续传。若提供短期缓存或其他重放能力，须在 3.5 明确保留范围、期限和失效行为。
- 无法补发历史事件时明确说明，并通过持久状态/结果查询补充。查询服务归 2.3，订阅衔接归 3.5，不另建一套工作流状态权威来源。
- done 表示本次 run 的流结束；等待审批、暂停、业务拒绝和成功分别保留真实状态。

## 四、验证与交付规则

- 契约和领域验证：非法路由、输入边界、归属、资格、金额及幂等。
- 图验证：实际编译图配合可控模型/服务，检查路由、父子状态、续接和预算。
- 数据库验证：独立测试数据中检查约束、状态转换、竞争和资源生命周期。
- 执行与 SSE 验证：受理、互斥、断开、重连、慢消费者、查询和崩溃边界。
- 恢复验证：在审批、支付与快照提交窗口注入必要故障，验证去重、恢复待办和核对。
- 端到端验证：核对领域服务或数据库结果，不能只断言回复。
- 真实模型与 Apifox：显式配置后单独联调，记录供应商、模型和场景，不进入默认付费测试。

各环节完成自身必要测试，9.2 负责跨场景验收。检查通过且无相关新变化时不重复扩大验证。纯文档修改核对事实、链接、编号和依赖即可。
