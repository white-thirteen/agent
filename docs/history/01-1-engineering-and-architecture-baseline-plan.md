## 3. 四项路线图调整的归属约束

本节记录用户已要求的边界调整，不展开后续环节的接口、表结构或技术实现，不改变九阶段、34 个二级环节。

| 调整 | 责任环节 | 需要在对应详细设计中落实的边界 |
| --- | --- | --- |
| 基础 Checkpoint 前置 | 3.3 | 基础 Checkpoint 的资源装配、快照读写、会话 thread 关联、跨轮续接和任务记录关联纳入 Runtime；在 3.3 明确存储与重启保证，不能把这些基础事项全部延后到 6.1 |
| 持久化中断与审批恢复 | 6.1，协同 6.3 | 6.1 重点处理持久化安全中断、嵌套子图恢复、重放、当前 run 上下文和审批恢复机制；审批业务记录与决定由 6.3 管理；复用 3.3 的基础能力 |
| 执行任务与崩溃边界 | 3.3 | 明确持久化任务记录与内存执行任务的区别；定义受理、互斥、异常退出、重启核对及可恢复范围；首版优先采用单进程执行和 PostgreSQL 记录的简单方案，不承诺任意位置或未知副作用的自动重试 |
| 订阅、重连、重放和查询 | 3.5，协同 2.3、1.3 | 断开仅释放订阅；重连不隐式创建新执行；明确重连能订阅哪些事件、是否支持重放及不支持时的行为；状态查询来自持久业务/执行记录；内存队列不自动具备 Last-Event-ID 重放能力 |

基础 Checkpoint 的持久化接入时点需要与 3.3 的崩溃保证一起定稿。若 3.3 承诺重启后延续快照，就必须在 3.3 落实相应持久化；若只支持识别未终结任务和显式重试，也必须明确限制，不能使用进程内 InMemorySaver 宣称重启恢复。1.1 仅登记这项待定决策，不替后续详细设计作出选择。

### 3.1 工具执行、策略和审批的责任边界

| 组件 | 主要职责 | 与其他组件的边界 |
| --- | --- | --- |
| ToolExecutePolicy（4.3） | 根据可信上下文、Agent、授权执行集合、权限、风险、预算和匹配的审批证据作出允许、拒绝或需要审批的判断 | 不创建审批决定，不执行工具，不以批准记录替代当前权限和业务条件检查 |
| ApprovalManager（6.3） | 管理审批申请与决定；核验审批人、操作、参数快照、workflow 和中断关联；处理幂等、冲突、失效及恢复待办 | 不直接执行支付/工具，不发放通用放行标记；向策略和恢复模块提供可核验的具体审批证据 |
| ToolExecutor（4.3） | 统一工具调用入口；进行 Schema 校验，调用策略，执行已允许调用，并处理超时、允许的重试和结果封装 | 不自行批准调用，不绕过 Policy；审批后重新进入执行入口并核验；确定性业务节点也使用该入口 |

Domain Service 在实际写入时仍校验归属、资格、金额、状态和业务幂等。上述三个组件不能代替业务事务约束。预算的计量和额度由 3.4 的统一机制提供，策略与执行器不能另建互不一致的计数体系。
