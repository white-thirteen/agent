## 实际缺陷与证据

[资源实验](../evidence/v2-02-task232-resource-runtime.json)在正式Runtime创建的Task/Run中消耗三次模型尝试；摘要请求配置上限256，但供应商known输出333。该次原始请求及finish_reason未捕获，不假装能追溯计量细节。资源输入比较6958→436本身为实测，但不能据此宣称硬输出预算已通过或阶段VERIFIED。

已安装langchain-openai的`ChatOpenAI._get_request_payload`会把`max_tokens`改写成`max_completion_tokens`。而[DeepSeek官方Chat API](https://api-docs.deepseek.com/api/create-chat-completion/)声明当前接口参数为`max_tokens`，[官方集成说明](https://api-docs.deepseek.com/quick_start/agent_integrations/oh_my_pi/)明确区分这两个字段。当前供应商为api.deepseek.com，参数适配缺陷已有源码和真实异常依据，不以提高配置限额掩盖。

当前摘要桥还未拒绝`finish_reason=length`；正确上限生效后，截断结果不能仍被视作完整Summary或发布Revision。

1. 最小修复当前DeepSeek参数适配，例如仅匹配当前官方host的小型ChatOpenAI子类，将最终payload中的字段映射回max_tokens；其他endpoint保持既有行为。不换模型、不升级全依赖、不新增Provider平台或发送两个字段碰运气。
