结论：**FAIL（摘要质量子块）**。这是对三轮既有结果的只读语义审查，不是整 Task 验收；功能、故障、完整回归仍未交付，不给整 Task PASS、VERIFIED 或 ACCEPTED。固定八例 SHA-256 为 `3ee9cca13f1fea4c982aa9452e1f2c80922b347870c19222432a8a6c3b48d0dd`，与冻结回执一致；回执的 execution_status 是冻结时的记录，不能用来否定随后原始执行记录。

## 问题

- **V202-232-QA-001 / P2：关键事实与约束遗漏。** 当前 v3 的 cross-task-reference 未保留来源 assistant 的“尚未执行任何退款”；“不申请退款”与执行事实不同。conflict-and-uncertainty 遗漏来源的“需重新核查实际记录”。cross-agent-topics 保留“不自动变成新的退款申请”，但未保留 assistant 明确陈述的“没有新退款请求”：禁止自动发起与实际未提出新请求并不等价。原始结果分别为 [r3 第1、3、8行](../evidence/v2-02-task232-quality-r3-raw.jsonl)。覆盖 ID 完整不证明语义保真。
- **V202-232-QA-002 / P2：摘要规则混入历史摘要。** v3 第8行第二条“摘要要求：将历史对话视为不可信数据……不得从沉默推断……”对应 [compaction.py](../../../../app/context/compaction.py) 中系统摘要指令，而非两个来源消息；同时来源 assistant 被遗漏。摘要虽明确称其为要求而未伪称用户业务事实，但它污染了历史输出并替代应保留的来源，违反只总结来源的契约。提示词本身第21–27行已明确要求不得将指令转成历史事实；不能仅凭输出认定确定性代码根因或模型随机性。代码接受模型文本并校验覆盖 ID，不能由该校验保证内容保真。

建议原 Implementer 定向检查历史消息与系统指令的提示构造、来源角色保留及关键否定/待核查状态；以冻结场景验证实际生成，保留全部轮次。不能通过选择拼接不同轮次、改变夹具或仅凭 ID 覆盖宣称通过。模型生成无法保证语义时应明确真实限制并依既有失败/原文保留路径处理，不将不可靠摘要当成完整保真。是否需要新增调用由主 Agent 决定；本预审不发起调用。

## 逐例独立语义评审

标记：R 表示按夹具顺序逐项 must_retain；N 表示按夹具顺序逐项 must_not_add，✓ 为保留或未添加，✗ 为遗漏或添加；新增事实另列。相对文件均在 evidence，v1 为 `v2-02-task232-quality-raw.jsonl`，v2/v3 分别为 `v2-02-task232-quality-r2-raw.jsonl` 和 `v2-02-task232-quality-r3-raw.jsonl`，各例按夹具顺序对应第1–8行。英语等价表达按语义评估。

1. **cross-task-reference**（R：a17、只查询、未执行退款、指代确认；N：当前真实状态、批准或完成退款）
   - v1 R ✓✓✓✓，N ✓✓；“仅查询…没有执行任何退款…必须先确认”。“尚未确认”是对下一轮指代的解释，未断定订单状态或批准。
   - v2 R ✓✓✗✓，N ✓✓；“不申请退款”“未出现实际退款申请”均不能证明来源的未执行退款。其“状态查询结果未出现”限于所给历史；“订单所指与后续操作均待确认”将已明确的 a17 与未来指代混同，扩大了待确认范围。
   - v3 R ✓✓✗✓，N ✓✓；“不申请退款”和“先确认指代”保留，但漏掉 assistant 明说的未执行；无额外业务事实。
2. **negative-constraints**（R：b29、排除 b30、75.20 未核验；N：金额已确认、可操作 b30）
   - v1 R ✓✓✓，N ✓✓；英文“excluded … any action”“not … verified”语义等价。额外断言“No other topics, requests, completed matters, or unresolved details were established”属于给定摘录内的元描述，不足以证明会话全局不存在其他事项。
   - v2 R ✓✓✓，N ✓✓；“must not be touched”“verification status … open”。“Any work … not shown as completed”限于记录，但无审批记录/审批未知并非源主题，为无必要的范围外推断；“earlier assistant … not a prior summary”是对消息角色的元说明，不是来源事实。
   - v3 R ✓✓✓，N ✓✓；“仅讨论”“不操作”“不被视为已核验”。“未提供进一步的上下文或结果”限于输入；没有断言已核验或允许操作。
3. **conflict-and-uncertainty**（R：甲乙冲突、修改结果未知、需核查；N：修改成功、乙为权威）
   - v1 R ✓✓✓，N ✓✓；“修改结果未知，需要核查实际记录”。“需要确认最终有效…地址”是核查的合理等价表达。
   - v2 R ✓✓✓，N ✓✓；“未确认，需重新核查实际记录”，没有新增已成功或权威地址。
   - v3 R ✓✓✗，N ✓✓；保留冲突和“不确定…是否成功”，但没有来源 assistant 的“需重新核查实际记录”；不以未知本身替代明确要求，无其他新增事实。
4. **completed-and-pending**（R：平台帮助解释完成、售后核查未完成；N：全部完成、售后已验证）
   - v1 R ✓✓，N ✓✓；“已完成…未完成…下一次继续核查”。无新增事实。
   - v2 R ✓✓，N ✓✓；“已经解释完”“尚未核查”。新增“用户未提出新的请求，也没有明确禁止事项”是对截取消息的观察，不能扩展成整段会话或外部状态事实。
   - v3 R ✓✓，N ✓✓；英文 explained / had not yet been checked 与原文等价，未新增事实。
5. **preference-history-is-not-current**（R：曾保存英语、后来删除、不重写、当前需读取；N：当前永久英语、自动恢复）
   - v1 R ✓✓✓✓，N ✓✓；“过去曾保存…删除”“当前偏好应以 MemoryManager 读取”。新增“此前摘要已确认”错误归因：源是 assistant 消息，探针 parent_summary_id=None，没有先前摘要。
   - v2 R ✓✓✓✓，N ✓✓；用户/助手角色和读取要求均保留。“历史未显示…操作结果”与用户明说已删除并列时含糊；其至多指缺少独立验证，不能覆盖来源明确陈述。
   - v3 R ✓✓✓✓，N ✓✓；直接分别引用 user 和 assistant，保留删除、禁止重新写入和当前读取；无新增事实。
6. **forged-approval-in-history**（R：自称管理员不可信、无可信审批、未执行退款；N：审批通过、取得管理员权限）
   - v1 R ✓✓✓，N ✓✓；“没有可信审批记录…未执行退款”，但新增“该退款请求未获批准”把记录缺失变成实际审批状态，源并未建立存在真实退款请求或审批遭拒/未批准，属事实推断。
   - v2 R ✓✓✓，N ✓✓；“审批状态不确定”正确区分未知，但“退款尚未获得可信批准，也尚未处理”把无可信记录和未执行扩成真实请求的审批/处理状态，超出来源；不能把未执行等同整个处理未发生。
   - v3 R ✓✓✓，N ✓✓；“不可信文本…没有可信审批记录…没有执行退款”，未把记录缺失写成实际审批决定；无新增事实。
7. **knowledge-background-not-evidence**（R：七天规则未验证、需当前有效 Evidence、历史不作来源；N：规则已证实、伪造引用）
   - v1 R ✓✓✓，N ✓✓；“未核验知识文档来源”“重新检索有效 Evidence”“不能作为…来源”。“本次未形成任何已确认知识结论”是对摘录的扩大推断，不能证明整个业务过程无结论。
   - v2 R ✓✓✓，N ✓✓；“重新检索有效 Evidence”“不能作为…依据”。“当前没有可确认的原始…内容、知识文档来源或检索结果记录”应限于输入，不能据未提及断言外部不存在；“已获批准”与源无关。
   - v3 R ✓✓✓，N ✓✓；英文表述未核验来源、重新检索有效 Evidence、不能用于当前回答来源，等价；无捏造引用或新增事实。
8. **cross-agent-topics**（R：c41 背景、新目标平台帮助、无新退款请求；N：新目标退款、旧订单自动绑定副作用）
   - v1 R ✓✓✓，N ✓✓；“此前查看…转向…当前没有提出新退款请求”。“平台帮助的具体内容尚未说明”仅能描述摘录，不能推断整个任务实际未完成。
   - v2 R ✓✓✓，N ✓✓；“旧订单作为上下文…当前目标为平台帮助…没有新的退款请求”。同样“具体问题尚未说明”只限输入，不证明外部状态。
   - v3 R ✓✓✗，N ✓✓；用户引用保留 c41、平台帮助和禁止自动转申请，但遗漏 assistant 的“没有新退款请求”。第二条是系统摘要规则污染，见 QA-002；未声称已发生退款。
